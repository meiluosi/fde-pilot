# 试点设计要点

指标字典、口径和因果链沿用 fde-problem-framing 的指标规范：技术 → 使用 → 业务，护栏横贯各层，箭头都是待验证的机制。本文只补试点特有的部分。

## 一、范围
- 小而可停：一个流程环节、一组明确的案件类型、一批自愿以外方式选出的使用者。
- 写明不含什么：沿用 Demo 复盘与定义卡的“本期不做”；手写件、人伤案件等被排除的类型不能事后悄悄并入分母。
- 试点不改变责任归属：人工复核、签字和兜底仍在原岗位，除非客户业务负责人书面变更。

## 二、指标字典（事前登记）
每项写：ID、层（技术/使用/业务/护栏）、定义、分子/分母、单位、基线（值、来源、时间窗）、目标、采集方法、责任岗位。至少包含使用、业务、护栏各一项。
- 使用层：有效使用 = 适格任务中真正用辅助完成的比例，不是页面打开次数或活跃账号数。
- 业务层：端到端工时、差错、返工、复核成本；复核和纠错时间必须计入，否则准确率提升可能不节时。
- 护栏层：严重漏检、越权、隐私、人工复核失效；平均值不能代替严重错误控制，稀有严重错用专项样本单独报。
- 基线与试点同口径。基线未知时先测基线，再启动；无法先测就把基线测量设计为试点前两周的并行任务。

## 三、对照与归因
| 设计 | 归因能力 | 备注 |
|---|---|---|
| 同期对照（交替/随机分配案件，或分组） | 最强 | 同一批人、同一时期；注意人为挑选案件 |
| 配对前后（同一对象试点前后，配对分析） | 中 | 受季节、案型、熟练度影响；记录混杂因素 |
| 前后对比（总体前后） | 弱 | 只能报告相关变化 |
| 无对照 | 无 | 只能报告使用与过程，不能宣称业务效果 |

选择无对照或前后对比时，方案里必须写归因限制，成效报告里业务效果最高判“部分”。

**最简方案臂**：如果条件允许，加一条非 AI 的最简替代方案作对照（规则、原文直出、流程改进），避免把改善都算给 AI，也避免把精力集中在链路优化上。来源：fde-demo 的回溯与 fde-problem-framing 的“传统方案能否解决”。

## 四、参与者与样本
- 选择方式写进方案。“自愿参加”会选进最积极、最熟练的人，结果偏乐观；尽量分层指定，或同时报告自愿者与非自愿者。
- 按案型、难度、资历、时间分层，至少记录这些维度。难例不能事后删除。
- 同一人处理的多件案件不是独立样本；报告时注明聚类，并优先按人汇总或使用能处理聚类的方法。
- 学习期（burn-in）：前 N 天不计入判定，N 与理由事前登记；学习期数据保留并单列。
- 最小有效窗口与样本：写明至少多少个工作日、多少件适格案件才进入判定。样本不足就判“部分”，不给结论。

## 五、护栏与停止条件
每条写：条件、动作、责任岗位，例如“S1：出现一起影响赔付金额的严重漏检｜暂停试点并回退人工｜风险负责人”。阈值由客户的风险负责人确认，不由我们单方设定。零观察错误不能证明零风险。

## 六、成败判据
- 成功、失败、延长三类判据都用指标 ID 写，业务层指标必须出现在成功判据里。
- “延长判据”指未达判定样本或窗口时怎么办，避免到期时临时改标准。
- 判据登记后不得替换。变更只能追加记录，写明原因、时间、批准人。

## 七、检查节奏
启动检查（开始前）、周检查（轻量）、期中检查（预警与停止条件）、结束判定。写明日期。每次检查都对照方案，不临时增加成败指标。
